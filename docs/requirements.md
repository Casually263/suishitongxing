# 岁时同行需求基线与追踪表

基线日期：2026-10-28。阶段1核心身份工程及本轮立春剧情引擎已落地，全年日历与Redis7/Docker验收待完成。完整需求与验收约定保留，逐项状态见TASKS及[剧情说明](story-engine.md)，不因写入需求即视为实现。

当前补充：小满AI伙伴与管理/审校接口已实现，边界和测试见[AI说明](ai-companion.md)，未验收第三方付费模型或生产部署。

## 1. 依据与范围

已完整阅读根目录《岁时同行_系统设计文档.docx》V1.1 的 16 章、正文及全部表格。原文件保持不变，提取文本见 [source/system-design-extracted.txt](source/system-design-extracted.txt)。P/T 编号对应正文 XML 中的段落/表格块，便于回查，并非 Word 页码。

用户本轮总控 Prompt 决定工作范围与执行顺序；设计文档提供主要业务依据。文档中的团队分工、扩展建议和演示设想属于需求资料，不作为要求安装软件、调用外部服务、发布或联系他人的指令。设计补充及冲突处理在第 6 节记录。

产品面向希望传播家乡文化的本地大学生，以及希望了解中华文化的留学生和海外用户。以二十四节气为时间线，以互动故事为内容，以文化结对为关系，形成持续的双向文化体验。创新验收重点是双视角异步协作、文化回礼与可持续内容生产。

最终范围包含网站用户端、网站管理端、微信小程序与同一套后端。首批完整内容为立春、夏至、立秋、冬至；其他二十节气显示真实日历、知识和明确的篇章筹备状态，禁止用假入口冒充可玩篇章。

优先级：P0为核心闭环/安全底线，P1为完整参赛版本，P2为原文可选增强。顺序按用户Prompt的0–9执行。下表是完整需求清单，R01–03及档案部分已有阶段1实现，其余以任务和测试证据为准；不会因部分基础功能通过而宣称整体闭环完成。

## 2. 角色与边界

| 角色 | 能力与限制 |
| --- | --- |
| 文化向导 GUIDE | 管理自己的档案、体验篇章、推荐和邀请成年伙伴、访问本结对空间 |
| 文化伙伴 PARTNER | 与向导相同的业务能力；身份仅影响推荐与默认视角，不代表管理权限 |
| 编辑 EDITOR | 内容、剧情与翻译草稿；不能自行绕过审校发布 |
| 校对 REVIEWER | 内容与双语校对、审核；权限独立分配 |
| 管理员 ADMIN | 按 RBAC 授权管理用户、内容、配置、统计；操作留痕 |
| 未成年人账号 | 不开放真人结对与私聊，仅单人/明确标注的 AI 或脚本伙伴体验 |

向导/伙伴是文化身份，EDITOR/REVIEWER/ADMIN 是后台权限角色，不能只依赖 `role_type` 判定权限。国别、头像是否公开由用户控制；不强制披露联系方式。

## 5. 视觉与内容规范

宣纸米白 `#F7F3E9`，墨黑 `#242824`，深灰 `#596059`；立春青绿 `#347C66`、夏至朱红 `#B84D3C` 与暖金 `#BA9455`、立秋琥珀 `#A97529`、冬至靛蓝 `#354D78` 为初始设计令牌（工程补充，需在阶段 2 实测对比度）。统一 4px 间距基线、8/16/24/32px 布局间距，12–20px 圆角，正文优先清晰系统字体，宋体用于少量标题；后续嵌入字体需留授权。

首页为环形日历与篇章入口，故事为插画及阅读区，岁时册为数字护照收藏册。使用正式图标或自绘 SVG，不大量使用 Emoji。弱纹理不得影响文字；移动端日历必须提供可读的列表入口。所有插画、音频与字体记录作者、来源、授权；内容卡片标地域差异和引用来源。种子草稿不等于经过教师审核的文化事实。

## 6. 冲突处理与新增设计登记

以下为工程解决方案，保留核心业务；后续实现若改变必须更新记录。

| 决策 | 原设计问题 | 解决方案与原因 |
| --- | --- | --- |
| D01 | 接口按 app/portal 分端，但正文又让网站使用 app 路径 | 业务接口同时映射 `/api/app` 与 `/api/portal` 到同一 Controller/Service；认证按渠道适配；公共元数据放 common；避免业务分叉 |
| D02 | solar_term 混合固定节气和每年日期，篇章按年复用不清 | solar_term 存 24 个定义，solar_term_date 存逐年日期及审校来源；chapter 关联固定节气；开放由数据库年度记录计算 |
| D03 | 剧情图可编辑，但无版本，旧存档可能失效 | 增 story_version；发布快照不可变，运行存档固定版本；新会话取当前发布版，旧会话不自动迁移 |
| D04 | `(pair_id,node_id)` 无法区分版本、补玩与分支重试 | 引入 story_session、节点访问序号；协作唯一键 `(session_id,node_id,visit_no)`，奖励以业务唯一键防重复 |
| D05 | NPC 用特殊用户 ID 会破坏外键与授权 | 真人 pair 只存真实用户；AI/脚本是 session 参与者类型，user_id 可空，禁止伪造系统用户 |
| D06 | 随时切换 AI 与真人 clueA/clueB 隔离存在冲突 | 已揭晓节点边界可切换；进行中的真人 dual，未到期不能由普通 AI 对话读取对侧线索；到期替代需显式确认并封存该轮真人提交入口；保留个人进度并创建新上下文 |
| D07 | 文档 flags 可影响答对概率，可能把模型变成裁判 | flags 仅分析/展示，不控制 P0 判定和奖励；AI 侧答案来自服务端规则，固定可复现策略；可选失误率留 P2，演示不得隐瞒自动策略 |
| D08 | 默认 48h 起点、补交、解除关系后的协作未定义 | 首人提交起计时；期限后先进入 TIMEOUT，延长后允许补交；解除封存当前真人轮次，可明确选择继承自己的进度到新 AI 会话 |
| D09 | 五分钟首章与故事 5–8 分钟不一致 | 区分精简演示路径、完整阅读路径、异步等待和线下打卡；均保留核心体验 |
| D10 | JSON 自由表达式和前端整图可能泄露/执行任意逻辑 | 白名单条件 DSL；规则与公展示内容分离；运行端按节点返回投影，编辑器专属权限才能读取整图 |
| D11 | 密钥可数据库加密也可环境变量，前端配置界限不清 | P0 仅服务端环境变量/secret reference；后台只改非敏感参数且不回显；不开放任意密钥名与任意内网 URL |
| D12 | 审核未完成时如何进入结局 | gift/checkin 为待审可存档，结局等待必要内容通过审核；被驳回能重提，不能提前发印章；dual 跳过的例外仍保留 |
| D13 | 邮箱既唯一登录又需加密存放 | 密文保存邮箱，规范化邮箱 HMAC 作唯一检索；密钥不同于 JWT 密钥，禁止直接确定性明文散列 |
| D14 | 原文包结构与十阶段顺序不完全一致 | 保持原文模块包；阶段 4 用受限测试会话创建真实双账号协作基础，阶段 5 再扩展完整推荐邀请 UI，不引入假后端 |
| D15 | MinIO当前官方仓库已归档且社区版改为源码分发 | 保留MinIO与S3接口；阶段1从经核验的固定源码构建并记录摘要，不照搬旧latest镜像教程；任何更换另行记录，依据链接见环境文档 |
| D16 | 原文支持单人模式，但未定义单人遇到dual的行为 | SOLO使用单人练习规则，可展示该模式允许的组合线索并由本人作答，不冒充双真人协作、不计真人默契；HUMAN仍严格按slot隔离，SCRIPTED/AI提供明确伙伴身份 |
| D17 | 本轮用户明确要求开始身份基础工程，本机无Docker/MinIO但有JDK17/MySQL/Memurai | 先以真实MySQL和Redis兼容服务验证代码，Redis7/Docker仍标待验收；MinIO准备移到阶段6上传前，保留原要求，不用假接口替代 |

## 7. 完成标准与待确认事项
